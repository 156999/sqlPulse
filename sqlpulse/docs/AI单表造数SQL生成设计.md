# AI 单表造数 SQL 生成设计

## 1. 背景与目标

造数页面已有单表表单模式：用户选择目标表、配置字段生成规则和生成条数，系统校验后按规则生成数据并提交造数任务。本设计在该表单流程中增加 AI SQL 生成功能。

用户不需要另写自然语言描述。AI 直接使用表单已收集的信息，生成指定条数的多条 `INSERT` SQL，并将结果放入现有 SQL 编辑区，供用户检查和提交。

目标是复用现有造数规则作为唯一规则来源，让生成 SQL 的字段和值遵守表单配置、目标表结构及表关系约束。

## 2. 范围

### 包含

- 入口位于“造数”页面的“单表表单”面板。
- 使用已选数据库连接、目标表、字段元数据、表单字段规则、生成条数和外键/唯一约束关系。
- AI 生成多条面向目标表的 `INSERT` 语句。
- 结果可预览、编辑，并应用到现有 SQL 模式编辑区。
- 生成过程进行结构化输出校验及 SQL 静态校验。

### 不包含

- 不要求用户输入自然语言业务描述。
- 不自动向依赖表写入数据；仅依据已读取的关系和可用父表数据生成目标表记录。
- 不自动执行生成的 SQL。
- 不替代现有表单规则引擎、占位符机制或造数任务执行器。
- 第一版仅支持当前单表表单选定的目标表，不生成多表 SQL。

## 3. 用户流程

1. 用户在造数页面选择连接和目标表。
2. 页面读取字段元数据和表关系，用户配置字段生成方式、参数和生成条数。
3. 用户点击“应用数据库规则”，现有规则校验通过。
4. 用户点击“AI 生成 SQL”。按钮仅在必要上下文齐备且规则校验通过时可用。
5. 后端将表结构、关系、规则及条数组装成受限上下文，调用用户配置的 AI 模型。
6. 后端校验模型结果。若失败，返回可读错误，不覆盖用户已有 SQL 内容。
7. 页面展示生成 SQL 预览与生成条数。用户可复制、编辑或点击“应用到 SQL 模式”。
8. 用户在现有 SQL 模式中检查并提交；执行仍由既有造数任务接口完成。

## 4. 页面交互

单表表单面板增加操作区：

```text
生成条数：[100]
[应用数据库规则] [AI 生成 SQL]
状态：已按数据库约束校验
```

AI 生成成功后展示结果区：

```text
已生成 100 条 INSERT（目标表：orders）
[展开/收起 SQL 预览]
[复制 SQL] [应用到 SQL 模式]
```

交互要求：

- 生成期间按钮显示忙碌状态并防止重复请求。
- 请求失败时保留表单、已有 SQL 和用户编辑内容。
- 在表、连接、生成条数或字段规则变化后，当前生成结果标记为过期；不自动覆盖或删除。
- “应用到 SQL 模式”应使用现有模式切换逻辑，并将 SQL 填入 SQL 编辑器；不得触发执行。
- 生成条数复用表单已有“INSERT 生成条数”字段，AI 输出语句数必须与其一致。

## 5. AI 输入上下文

后端从可信数据库元数据和页面提交的规则构建上下文，不直接信任客户端声称的 schema 或关系。连接解析和元数据读取复用造数服务。

输入至少包括：

### 5.1 表信息

- 数据库类型（当前仅 MySQL）。
- 当前 schema、目标表名。
- 列名、数据库类型、长度/精度、是否可空、默认值、是否自增、是否生成列。
- 主键、唯一索引、CHECK 约束（若现有元数据服务提供）。

### 5.2 表关系

- 目标表外键列到父表/父列的映射。
- 关系涉及的唯一约束，尤其联合唯一索引。
- 必要时提供父表可用样本值；只提供生成记录实际需要的最小样本，避免把整表数据发给模型。
- 父表无可用值或无法安全读取时，明确告知该外键无法推断，不能编造引用值。

### 5.3 表单规则

每列的有效规则应采用服务端复核后的规则，例如：

- `omit`：省略该列，由数据库默认值/自增逻辑处理。
- `rand` / `randf`：范围及小数精度。
- `pick` / `pickw`：枚举候选值及权重。
- `randstr`：长度和字符范围。
- `randdate` / `randdt`：日期时间范围。
- `uuid`、固定值、sample 及其参数。
- 唯一性、空值比例、外键来源等已配置约束。

缺失、无效或未应用的规则不得静默交给模型猜测；接口应返回需要先补齐/应用规则的字段列表。

## 6. 生成约束

系统提示应明确要求模型：

1. 仅生成针对当前目标表的 MySQL `INSERT` 语句。
2. 仅写入表单规则允许生成的列；省略 `omit`、自增、生成列和未显式覆盖的默认值列。
3. 每个显式写入字段必须存在于目标表，值的类型、范围、长度、精度和枚举值必须满足规则。
4. 生成的记录数必须精确等于请求条数。
5. 满足主键、唯一索引和联合唯一约束；不能通过随机猜测声称满足唯一性。
6. 外键值必须来自可信父表样本或系统明确提供的可用值，不得虚构父表记录。
7. 不输出 DDL、UPDATE、DELETE、事务控制、存储过程、注释中的可执行内容或其他表的写入语句。
8. 以 JSON 结构返回 SQL 语句数组及简短校验摘要，不添加 Markdown 围栏或额外文本。

建议输出结构：

```json
{
  "statements": ["INSERT INTO `orders` (`amount`) VALUES (12.50)", "..."],
  "notes": []
}
```

若上下文不足以同时满足规则，模型应返回明确的不可生成原因；服务端不得用不满足规则的 SQL 兜底。

## 7. 服务端校验与安全边界

AI 输出视为不可信文本。通过校验后才返回前端：

- JSON 结构合法，`statements` 为非空数组且数量等于请求条数。
- 每条语句只能是单条 `INSERT`，拒绝多语句拼接、注释注入和其他 SQL 类型。
- 使用 SQL parser 或现有可靠解析工具解析语句；不以简单关键字正则作为唯一安全校验。
- 所有语句目标表必须与请求目标表一致；列名必须属于该表，且不得包含生成列等禁止列。
- 值数量与列数量匹配；对字面量可执行的类型、长度、精度、枚举及规则范围校验。
- 所有规则强制项均须逐行满足；唯一性、外键和跨行规则须结合整批数据检查。
- 不执行模型生成的 SQL，不使用 `EXPLAIN` 作为生成安全性的替代检查。
- 错误响应不包含 API Key、连接密码或未经清洗的模型请求头信息。

如果仓库当前没有可覆盖 MySQL 方言的解析器，需在实现阶段评估依赖或采用严格限定的 SQL 子集；在可靠解析校验完成前，不应将 AI 输出直接作为可提交 SQL。

## 8. 接口草案

新增受登录保护的接口，例如：

```http
POST /api/datagen/ai/generate-sql
Content-Type: application/json
```

请求沿用连接选择约定，并包含：

```json
{
  "connection_id": "...",
  "table": "orders",
  "row_count": 100,
  "rules": []
}
```

临时连接场景沿用现有 `db_dsn` 请求模型，敏感信息只经请求体传输，不写日志。服务端应重新读取元数据并验证用户身份、连接归属、表名、行数上限和规则，而非信任前端元数据。

成功响应：

```json
{
  "ok": true,
  "table": "orders",
  "statement_count": 100,
  "sql": "INSERT ...;\nINSERT ...;"
}
```

模型配置复用个人资料页的厂商/模型偏好和密钥解析逻辑。缺少可用密钥时返回明确的配置引导错误，不回退到未经用户选择的其他密钥。

## 9. 失败处理

| 情况 | 页面反馈 |
|---|---|
| 未选择目标表/未读取元数据 | 提示先选择目标表并读取字段 |
| 规则未应用或校验失败 | 展示字段规则错误，要求先修复 |
| 未配置可用 AI 密钥 | 提示到个人资料配置 AI 模型 |
| 外键无可用父表样本 | 指明对应外键字段，提示先准备父表数据或调整规则 |
| 唯一组合空间不足 | 指出约束名和可生成数量/冲突原因 |
| 模型超时、限流或服务错误 | 展示可重试错误，不清空已填数据 |
| 模型输出格式/SQL 校验失败 | 不展示为可用结果；提示重试或检查规则 |

## 10. 与现有造数链路的关系

AI 入口是现有单表表单和 SQL 模式之间的桥接能力：

```text
表单字段规则 + 表元数据 + 表关系
                ↓
             AI 生成
                ↓
       服务端校验后的多条 INSERT
                ↓ 用户检查并应用
          现有 SQL 模式
                ↓ 用户提交
       现有造数任务执行链路
```

AI 生成不创建独立执行器和任务状态机。提交、日志、停止、执行权限及 SQL 长度限制继续由现有造数流程处理。

## 11. 验收标准

1. 用户无需输入自然语言描述即可从已配置的单表表单发起生成。
2. 后端使用目标表真实 schema、关系和服务端校验后的表单规则。
3. 生成 SQL 条数与表单生成条数一致，且只写目标表。
4. 违反字段规则、表关系、唯一约束或 SQL 类型的模型输出被拒绝。
5. 生成结果可预览、复制和应用到 SQL 模式，但生成动作本身不执行 SQL。
6. 应用结果后能沿用现有 SQL 造数流程提交。
7. 生成失败不会覆盖已有 SQL 或丢失表单配置。
8. 未配置 AI、权限不匹配、非法表名、超限行数等情况均有明确错误反馈。

## 12. 实施拆分建议

1. 定义 AI 生成请求/响应模型，复用现有 AI provider、用户密钥和模型偏好读取逻辑。
2. 编写服务端上下文组装器：读取真实元数据、关系、有效表单规则及所需父表样本。
3. 实现受约束的模型调用、JSON 解析和输出 SQL 校验。
4. 在造数表单面板加入生成按钮、忙碌态、错误反馈、SQL 预览和应用操作。
5. 将结果接入现有 SQL 编辑器和模式切换状态，不触发任务提交。
6. 覆盖规则映射、错误拒绝、条数匹配、目标表限制和前端不覆盖已有内容等用例。
