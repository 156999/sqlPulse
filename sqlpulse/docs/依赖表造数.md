# 依赖表造数设计方案

## 一、背景

当前造数功能支持根据目标表字段规则生成 INSERT 语句，并能根据数据库元数据识别外键、主键、唯一索引等约束。

在类似 `ec_order_items` 的明细表场景中，目标表通常同时具备以下约束：

```sql
order_id -> ec_orders.id
sku_id   -> ec_product_skus.id
UNIQUE KEY uk_ec_order_items_order_sku (order_id, sku_id)
```

这会导致目标表的可生成空间不只取决于自身字段规则，还取决于父表数据量和目标表已有组合。

例如：

```text
ec_orders 可用 id：2 个
ec_product_skus 可用 id：3 个
理论组合数：2 * 3 = 6
ec_order_items 已有组合：6 个
剩余可用组合：0 个
用户目标：生成 100 条 ec_order_items
```

此时继续随机重试没有意义，任务必然失败。系统应在执行前识别依赖表，向用户展示影响范围，并在用户允许时自动补充依赖表数据。

## 二、设计目标

1. 在用户选择目标表造数时，自动分析目标表依赖的父表。
2. 在执行前向用户展示本次造数会影响哪些表，以及为什么需要这些表。
3. 对联合唯一约束涉及外键字段的场景，预估可用组合空间。
4. 当可用组合不足时，给出明确原因和补数建议。
5. 在用户确认后，按依赖顺序自动补充父表，再生成目标表。
6. 保持默认行为保守，避免用户无感知地向大量上游表写入数据。

## 三、核心概念

### 1. 目标表

用户当前选择并希望生成数据的表。

示例：

```text
ec_order_items
```

### 2. 直接依赖表

目标表外键直接引用的父表。

示例：

```text
ec_order_items.order_id -> ec_orders.id
ec_order_items.sku_id   -> ec_product_skus.id
```

直接依赖表为：

```text
ec_orders
ec_product_skus
```

### 3. 完整依赖链

直接依赖表继续向上追溯外键后得到的完整上游表集合。

示例：

```text
ec_customers -> ec_orders -> ec_order_items
ec_products  -> ec_product_skus -> ec_order_items
```

完整依赖链可能包含：

```text
ec_customers
ec_products
ec_product_skus
ec_orders
ec_order_items
```

### 4. 组合空间

当目标表存在联合唯一索引，且索引字段来自父表 sample 时，可以计算理论组合空间。

示例：

```sql
UNIQUE KEY uk_ec_order_items_order_sku (order_id, sku_id)
```

组合空间：

```text
理论组合数 = ec_orders 可用 id 数 * ec_product_skus 可用 id 数
剩余组合数 = 理论组合数 - ec_order_items 已有唯一组合数 - 本任务已生成组合数
```

## 四、用户故事

### 场景一：仅分析，不自动补表

用户选择：

```text
目标表：ec_order_items
生成条数：100
策略：仅生成目标表
```

系统展示：

```text
检测到 ec_order_items 依赖以下表：

1. ec_orders
   原因：ec_order_items.order_id 引用 ec_orders.id

2. ec_product_skus
   原因：ec_order_items.sku_id 引用 ec_product_skus.id

联合唯一约束：
ec_order_items(order_id, sku_id)

当前可用组合：
ec_orders.id：2 个
ec_product_skus.id：3 个
理论组合数：6
目标表已占用组合：6
剩余可用组合：0

当前配置不足以生成 100 条数据。
```

用户可以选择手动补父表，或切换到自动补依赖表策略。

### 场景二：自动补充直接依赖表

用户选择：

```text
目标表：ec_order_items
生成条数：100
策略：自动补充直接依赖表
```

系统展示：

```text
本次将顺带生成以下依赖表数据：

ec_orders：建议补充 18 条
ec_product_skus：建议补充 7 条
ec_order_items：生成 100 条

原因：
ec_order_items.order_id 需要引用 ec_orders.id
ec_order_items.sku_id 需要引用 ec_product_skus.id
ec_order_items(order_id, sku_id) 必须唯一

预计补充后组合空间：
ec_orders.id：20 个
ec_product_skus.id：10 个
理论组合数：200
扣除已有组合：6
预计剩余组合：194
```

用户确认后，系统按顺序执行：

```text
1. ec_orders
2. ec_product_skus
3. ec_order_items
```

### 场景三：自动补充完整依赖链

用户选择：

```text
策略：自动补充完整依赖链
```

系统继续追溯父表外键，展示完整计划：

```text
ec_customers：补充 18 条
ec_products：补充 7 条
ec_product_skus：补充 7 条
ec_orders：补充 18 条
ec_order_items：生成 100 条
```

执行顺序通过拓扑排序得到：

```text
ec_customers -> ec_products -> ec_product_skus -> ec_orders -> ec_order_items
```

## 五、页面设计

### 1. 新增依赖影响范围面板

在造数配置页中增加面板：

```text
依赖影响范围

目标表：
ec_order_items，计划生成 100 条

检测到依赖：
ec_orders
  ec_order_items.order_id -> ec_orders.id

ec_product_skus
  ec_order_items.sku_id -> ec_product_skus.id

联合唯一约束：
uk_ec_order_items_order_sku(order_id, sku_id)

当前组合空间：
理论组合数：6
已占用组合：6
剩余可用组合：0
```

### 2. 造数策略选择

提供三种互斥策略：

```text
仅生成目标表
不自动写入依赖表。适合父表数据已经充足的情况。

自动补充直接依赖表
只补充目标表直接引用的父表。推荐默认策略。

自动补充完整依赖链
从最上游父表开始补充。适合一键初始化完整业务链路。
```

默认推荐：

```text
自动补充直接依赖表
```

### 3. 依赖补数计划确认

当系统建议自动补表时，展示确认表格：

| 表名 | 计划动作 | 计划条数 | 原因 |
|---|---:|---:|---|
| ec_orders | 补充 | 18 | 扩大 order_id 候选空间 |
| ec_product_skus | 补充 | 7 | 扩大 sku_id 候选空间 |
| ec_order_items | 生成 | 100 | 用户选择的目标表 |

用户需要显式确认：

```text
[x] 我知道本次会向依赖表写入数据
```

### 4. 高级选项

```text
[ ] 只分析，不执行
[ ] 包含完整上游依赖链
[ ] 允许覆盖默认建议条数
[ ] 父表已足够时不补充
```

### 3. 执行接口扩展

现有造数执行接口增加依赖计划参数：

```json
{
  "target_table": "ec_order_items",
  "target_rows": 100,
  "dependency_strategy": "direct_dependencies",
  "dependency_plan": {
    "ec_orders": 18,
    "ec_product_skus": 7
  },
  "confirm_dependency_writes": true
}
```

后端必须校验：

1. `confirm_dependency_writes` 为 true 才能写依赖表。
2. 实际执行前重新读取元数据，避免页面计划过期。
3. 若用户传入的计划条数小于当前所需，应阻止执行或再次提示。
4. 每生成完一个父表后，刷新 sample 缓存。

## 七、补数数量算法

### 1. 基础公式

```text
required_space = target_rows * safety_factor
```

推荐：

```text
safety_factor = 2
```

对于 `ec_order_items`：

```text
target_rows = 100
required_space = 200
```

### 2. 两个父表的场景

当前：

```text
orders = 2
skus = 3
current_space = 6
```

目标：

```text
orders * skus >= 200
```

推荐补到较均衡的规模：

```text
orders = ceil(sqrt(200)) = 15
skus = ceil(200 / 15) = 14
```

也可以结合业务语义设置偏好：

```text
订单通常多于 SKU：orders = 20, skus = 10
SKU 通常多于订单：orders = 10, skus = 20
```

第一版建议使用均衡算法，避免引入复杂业务配置。

### 3. 多个父表的场景

当联合唯一索引包含多个 sample 字段：

```text
space = count_a * count_b * count_c
```

补数策略：

1. 优先补候选数最少的父表。
2. 每次补到接近 `required_space` 的 n 次方根。
3. 达到 required_space 后停止。

伪代码：

```text
counts = 当前各父表候选数
required = target_rows * safety_factor

while product(counts) < required:
    min_table = 候选数最少的表
    counts[min_table] += 1
```

### 4. 已占用组合修正

最终要考虑目标表已有组合：

```text
available_space = product(candidate_counts) - occupied_combinations - task_used_combinations
```

所以补数目标应满足：

```text
available_space >= target_rows
```

更保守：

```text
available_space >= target_rows * safety_factor
```

## 八、执行顺序

### 1. 拓扑排序

构建依赖图：

```text
父表 -> 子表
```

示例：

```text
ec_customers -> ec_orders
ec_orders -> ec_order_items
ec_products -> ec_product_skus
ec_product_skus -> ec_order_items
```

排序结果：

```text
ec_customers
ec_products
ec_orders
ec_product_skus
ec_order_items
```

### 2. 循环依赖处理

如果检测到循环依赖：

```text
A -> B
B -> A
```

第一版不自动处理，直接阻止自动补表：

```text
检测到循环外键依赖，无法自动确定安全造数顺序，请手动处理。
```

### 3. 执行后刷新缓存

每个表执行完成后：

1. 提交当前表生成结果。
2. 清理 sample 缓存。
3. 重新读取下游表需要的父表候选值。
4. 再执行下一个表。

## 十、安全策略

1. 自动补表必须要求用户确认。
2. 默认只补直接依赖表，不默认追溯完整依赖链。
3. 每个依赖表补充条数必须有上限。
4. 自动补表前后都要记录日志。
5. 不允许自动删除、覆盖或修改已有数据。
6. 只允许通过已有字段规则或数据库规则生成依赖表数据。
7. 如果父表存在无法自动满足的非空字段、唯一字段或业务校验，依赖补表计划应标记为不可自动执行。
8. 遇到循环外键、复合外键、不支持的生成规则时，应降级为只分析并提示用户。

依赖面板可分为以下状态：

```text

父表不足，但无法自动补充
依赖计划已确认

执行完成
执行失败
```

### 状态示例

父表充足：

```text
可用组合 280，目标生成 100 条，当前父表数据充足。
```

父表不足，可自动补充：

```text
可用组合 0，目标生成 100 条。
建议补充 ec_orders 18 条、ec_product_skus 7 条。
```

父表不足，但无法自动补充：

```text
ec_orders 存在必填字段 payment_address，但没有可用生成规则。
请先配置 ec_orders 的字段规则。
```

## 十三、分阶段实施

### 阶段一：依赖分析和展示

目标：

1. 读取外键依赖。
2. 读取唯一索引。
3. 计算联合唯一组合空间。
4. 页面展示依赖影响范围。
5. 父表不足时提前提示，不进入随机重试。

不做自动补表。

### 阶段二：直接依赖表自动补数

目标：

1. 支持用户确认后自动补直接父表。
2. 根据组合空间估算补充条数。
3. 按父表 -> 目标表顺序执行。
4. 每个父表执行后刷新 sample 缓存。

只处理一层依赖。

### 阶段三：完整依赖链

目标：

1. 支持递归追溯上游依赖。
2. 使用拓扑排序生成执行顺序。
3. 检测循环依赖并阻止自动执行。
4. 展示完整影响范围。

### 阶段四：智能补数策略

目标：

1. 支持用户配置安全系数。
2. 支持按业务偏好分配父表补数比例。
3. 支持保存常用依赖补数模板。
4. 支持执行后对比计划值和实际影响行数。

## 十四、验收标准

1. 用户选择 `ec_order_items` 生成 100 条时，页面能展示依赖表 `ec_orders` 和 `ec_product_skus`。
2. 页面能说明依赖原因：`order_id` 引用 `ec_orders.id`，`sku_id` 引用 `ec_product_skus.id`。
3. 页面能展示联合唯一约束 `order_id + sku_id`。
4. 当前组合空间不足时，系统能提前给出可读提示。
5. 用户开启自动补直接依赖表后，系统能展示将补哪些表和补多少条。
6. 执行日志能记录依赖计划、执行顺序、每个表的生成结果。
7. 父表补充完成后，目标表能使用新的父表数据继续生成。
8. 用户未确认依赖写入时，系统不会自动向父表写入数据。
